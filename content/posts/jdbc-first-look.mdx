MySQL에 테이블을 만들고, 자바에서 JDBC로 조회하는 단계예요. 화면 없이 콘솔 출력만 하는 작업이었습니다.

## 커넥션이 뭔지 모르는 채로 커넥션 풀 설명을 읽었어요

"커넥션 생성이 느리다"는 문장부터 만났는데, **커넥션이 뭔지 모르면 커넥션 풀이 왜 나왔는지도 알 수 없어요.**

순서를 거꾸로 잡고 개념 지도를 먼저 그렸습니다.

```
DriverManager → Connection → Statement → ResultSet
                                  (닫을 때는 역순)
```

## 실패했는데 종료코드가 0이었어요

이게 이 날의 제일 큰 수확이었습니다.

MySQL을 끄고 프로그램을 돌렸어요. 예외 스택은 화면에 잘 찍혔습니다. 그런데 종료코드를 확인해보니 **0**이었어요.

```bash
echo $?   # 0 ← 성공
```

원인은 `printStackTrace()`였습니다. **이건 화면에 찍기만 하고 프로그램은 정상으로 끝냅니다.** 예외를 잡아서 출력하고 넘어간 거죠.

<Callout>
왜 사고냐면, **배포 스크립트와 CI는 종료코드로 판단**하기 때문이에요. DB가 죽었는데 "정상 시작"으로 보고되면 아무도 알림을 못 받습니다.
</Callout>

프론트에서 `npm test`가 실패하면 CI가 멈추는 것과 같은 메커니즘이었어요. 이미 아는 거였는데 자바에서 만나니 못 알아봤습니다.

## try-with-resources 방향을 반대로 알았어요

"괄호 안에 넣은 걸 빼면 어떻게 되나요"라는 질문에 두 번 헛답을 했습니다.

**괄호가 닫아주는 쪽**이에요. 괄호 안에 넣으면 자동으로 닫아주고, 안 넣으면 내가 닫아야 합니다. 저는 반대로 이해하고 있었어요.

## PreparedStatement를 쓰는 이유는 두 개예요

교재에 "매개변수 처리에 특화"라고만 적혀 있어서 무슨 말인지 몰랐는데, 실체는 두 가지였습니다.

**보안** — `?`에 들어간 값은 **항상 값으로만** 취급돼요. SQL 문법으로 해석되지 않으니 SQL 인젝션이 안 됩니다.

**성능** — 틀이 고정이라 DB가 한 번 분석한 걸 재사용할 수 있어요.

## 상속 구조를 알면 외울 게 줄어요

```
Statement ← PreparedStatement ← CallableStatement
```

`CallableStatement`가 `PreparedStatement`와 비슷하게 생긴 건 **물려받아서**예요. 따로 외울 게 아니었습니다.

## ResultSet 커서가 첫 행 "앞"에서 시작하는 이유

처음엔 불편하다고 생각했는데 설계 의도가 있었어요.

`next()` 하나가 **이동과 존재 확인을 겸합니다.** 그래서 0건일 때와 여러 건일 때를 같은 패턴으로 처리할 수 있어요.

```java
while (rs.next()) {
    // 0건이면 아예 안 들어오고, 여러 건이면 반복
}
```

## 셋을 다, 역순으로 닫는 이유

`Connection`·`Statement`·`ResultSet`은 자바 객체이면서 **DBMS 쪽 자원(커서·핸들·세션)을 붙들고 있어요.** 자바의 가비지 컬렉터는 건너편 DB 자원을 모릅니다.

그래서 직접 닫아야 하고, **꺼낸 것부터** 닫습니다. 소속 관계의 역순이에요.

## 프로시저는 예시를 보고서야 이해했어요

"DBMS에 저장된 SQL 묶음"이라는 설명으로는 감이 안 왔습니다. 구체적인 예를 보고 넘어갔어요.

글 삭제를 한다고 하면 실제로는 세 가지를 해야 합니다.

```
1. 댓글 삭제
2. 글 삭제
3. 로그 INSERT
```

이 묶음에 이름을 붙여서 DB에 저장해두고 이름으로 부르는 것 — 그게 프로시저였어요. 단골 카페에서 "늘 마시던 걸로요" 하는 것과 같습니다.

**트리거와 헷갈리기 쉬운데** 부르는 사람이 달라요. 프로시저는 **내가** 부르고, 트리거는 조건이 되면 **DBMS가 알아서** 실행합니다.

## AUTO_INCREMENT는 번호를 재사용하지 않아요

3번을 지워도 다음은 4번이에요. **id에 구멍이 나는 게 정상이지 버그가 아닙니다.**

## 남은 것

- **실패했는데 종료코드 0인 게 제일 위험해요.** `printStackTrace()`는 찍기만 하고 성공으로 끝냅니다.
- **PreparedStatement는 보안과 성능 둘 다예요.**
- **DB 자원은 직접, 역순으로 닫습니다.** GC가 건너편을 모르니까요.
- **추상 설명이 안 통하면 구체 예시를 찾습니다.** 프로시저가 그랬어요.

## 아직 모르는 것

- **커넥션 풀** — "커넥션 생성이 느리다"의 해법. 서블릿은 안 끝나는 프로그램인데 요청마다 만들고 닫으면 무슨 일이 생기는지
- **JDBC가 전부 인터페이스인 이유** — 구현체는 MySQL 드라이버 안에 있어요. 왜 이렇게 설계했는지
- **`printStackTrace()` 대신 뭘 쓰나** — 로그로 남기기 vs 예외를 위로 다시 던지기
