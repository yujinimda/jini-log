게시판 테이블을 설계하고, 자바 쪽 도메인 객체를 처음 만들었어요. DB 설계와 자바 클래스를 둘 다 처음 해봤습니다.

## 외래키를 반대 테이블에 넣었어요. 세 번이나요

`board`가 `category`를 가리키는 관계인데, `category`에 `category_id`를 넣었습니다. **자기가 자기 번호를 또 드는 꼴**이었어요.

데이터로 그려보니 바로 보였습니다.

```
category                  board
 id | name                 id | category_id | title
 1  | JAVA                 1  |      1      | 서블릿이란
 2  | Database             2  |      1      | JDBC
                           3  |      2      | MySQL 설치
```

**가리키는 쪽이 상대의 번호를 적어둡니다.** `category`에는 `category_id`가 없어요. 자기 번호는 이미 `id`니까요.

외우기 쉽게 정리하면 이래요. 그 테이블에 `_id`로 끝나는 컬럼이 있으면 그 컬럼마다 외래키 선언이 하나씩 필요합니다. 없으면 외래키 선언도 없어요.

그리고 외래키는 **두 줄 세트**입니다.

```sql
category_id BIGINT NOT NULL,                       -- 컬럼
FOREIGN KEY (category_id) REFERENCES category(id)  -- 설명
```

설명만 쓰고 컬럼을 안 만들어서 계속 에러가 났어요.

## `VARCHAR(3-5)`처럼 범위를 쓰려고 했어요

명세가 "3자 이상 5자 미만"이라 그대로 적었습니다. `VARCHAR`는 **최대 길이 하나**만 받아요. 그리고 "5 미만"이니 최대는 4입니다.

**최솟값은 DB가 안 막아줘요.** 코드에서 해야 합니다.

## 프론트 검증이 무슨 의미인지 의심했어요

자바 쪽 setter가 아무 검사 없이 값을 통과시키는 걸 보고 "그럼 프론트에서 검증하는 게 무슨 의미냐"고 물었어요. **이 의심이 맞았습니다.**

**프론트 검증은 방어가 아니에요. 사용자에게 빨리 알려주는 친절함입니다.** 프론트 코드는 사용자 손에 있어서 신뢰할 수 없어요 — `curl`로 직접 보내면 통째로 건너뜁니다.

층이 셋이고 목적이 달라요.

```
프론트    빠른 안내       (건너뛸 수 있음)
서버      실제 방어       ← 진짜는 여기
DB        마지막 그물     (NOT NULL, 길이 제한)
```

## `private`이 왜 필요한지 납득이 안 갔어요

getter와 setter를 다 열어둘 거면 `private`이 무슨 의미냐고 물었습니다. 그리고 setter가 아무 검사도 안 하는데 직접 접근을 막는 게 소용이 있냐고 되물었어요.

**지금은 소용없다는 게 맞는 답이었습니다.**

setter가 그냥 대입만 하니까 `private`을 붙여도 실질 차이가 0이에요. 두 길이든 한 길이든 같은 값이 들어갑니다.

`private`이 하는 일은 값을 막는 게 아니라 **"나중에 검사를 넣을 자리를 한 곳으로 보장하는 것"**뿐이에요. 검사가 없으면 보장할 게 없어서 아무 일도 안 합니다.

실제로 값을 막는 건 서버 진입점 검증과 DB 제약이고, `private`은 거기 안 껴요.

<Callout>
그래서 지금 `private`을 쓰는 정직한 이유는 이 정도예요 — 자바 관습이라 남이 읽을 때 예상대로고, JSP가 getter를 요구합니다.
</Callout>

이 비판은 저만 하는 게 아니어서 자바에 `record`가 생겼어요. `record`는 getter를 자동으로 만들고 **setter는 없습니다.** "만든 뒤엔 안 바뀐다"를 기본으로 삼은 거예요.

## getter/setter 노가다에서 사고가 났어요

필드 8개 × 2 = 16개 메서드를 손으로 썼습니다. 그 와중에 이런 게 나왔어요.

```java
public void setUpdated_at(LocalDateTime created_at) {
    this.created_at = created_at;   // updated_at 에 넣어야 하는데
}
```

복사해서 붙이고 안 바꾼 겁니다.

**컴파일 에러가 안 나요.** 수정일시를 넣으면 등록일시가 바뀝니다. 글을 수정할 때마다 등록일시가 덮어써져요. 값이 그럴듯해서 화면만 봐선 못 알아챕니다.

## 에디터 색깔을 안 믿고 DB에 물어봤어요

`comment`가 파란 글씨로 나와서 예약어인 줄 알았는데, MySQL에 직접 물어보니 아니었습니다.

```sql
SELECT WORD, RESERVED FROM INFORMATION_SCHEMA.KEYWORDS WHERE WORD = 'COMMENT';
```

`comments`는 MySQL에 아예 없는 단어인데도 에디터는 색을 칠했어요. 하이라이터가 자기 나름의 목록을 쓰는 거지 MySQL 기준이 아닙니다.

## 남은 것

- **외래키는 가리키는 쪽이 들어요.** 그리고 컬럼 선언과 외래키 선언은 두 줄 세트입니다.
- **DB 제약은 최댓값만 막아요.** 최솟값과 형식은 코드 몫입니다.
- **프론트 검증은 방어가 아니라 안내예요.** 서버가 다시 검사해야 합니다.
- **`private`은 값을 막지 않아요.** 검사를 넣을 자리를 보장할 뿐이고, 검사가 없으면 아무 일도 안 합니다. 관습으로 쓰는 걸 인정하고 쓰는 게 정직해요.
- **에디터 색은 참고, DB가 판정.** 도구의 표시를 사실로 믿으면 안 됩니다.
- **손으로 반복하는 코드에서 사고가 나요.** 복사·붙여넣기 후 안 바꾼 한 줄이 컴파일도 통과하고 값도 그럴듯해서 제일 늦게 발견됩니다.

## 아직 모르는 것

- `record`를 이 프로젝트에 써보면 어떤지
- 목록에서 안 채우는 필드가 `null`로 남는 게 나중에 사고를 내는지
